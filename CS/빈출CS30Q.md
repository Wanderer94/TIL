1. [데이터베이스] 인덱스(Index)의 작동 원리와 B-Tree 구조

    • 출제 의도: 스프링 시큐리티를 단순 라이브러리 설정 복사로 쓰는 게 아니라, 서블릿 컨테이너와 스프링 컨테이너 사이의 가교 역할 및 보안 컨텍스트의 내부 동작 매커니즘을 꿰뚫고 있는지 검증합니다.
    • 좋은 답변 핵심: DelegatingFilterProxy가 서블릿 필터 요청을 받아 스프링 빈으로 등록된 FilterChainProxy에 위임하는 구조. 인증 객체(Authentication)가 ThreadLocal 기반의 SecurityContextHolder에 저장되어 요청이 처리되는 동안 전역적으로 공유되는 원리 기술.
    • 자주 하는 실수: 시큐리티 필터가 스프링 MVC의 인터셉터(Interceptor)와 완전히 같은 순서로 돈다고 생각하는 오류(Filter는 서블릿 단계, Interceptor는 스프링 디스패처 서블릿 내부 단계에서 동작함). 비동기 스레드(@Async 등)를 띄웠을 때 ThreadLocal의 인증 정보가 기본적으로 공유되지 않는 문제를 인지하지 못하는 경우.

    • 중요도: ★★★★☆ (고급)
30. [시스템 설계 기초] 캐시 무효화(Cache Invalidation) 문제와 데이터 정합성 보장 전략
    • 출제 의도: 캐시를 적용해 성능을 올린 후 반드시 마주치게 되는 데이터 불일치(Stale Data) 문제를 정교하게 해결하는 백엔드 아키텍처 마스터링 단계를 평가합니다.
    • 좋은 답변 핵심: 원본 DB 데이터가 수정되었을 때 캐시를 어떻게 동기화할 것인가의 문제. 즉시 삭제(Cache Eviction) 방식과 즉시 갱신(Cache Update) 방식의 장단점. 고성능이 필요할 때 Read/Write를 캐시에 먼저 하고 CDC(Change Data Capture) 패턴이나 카프카 이벤트를 통해 DB를 최종 동기화하는 구조 설계 역량.
    • 자주 하는 실수: 단순하게 "데이터 수정할 때 Redis 컬럼도 수정 코드 한 줄 넣으면 된다"고 답하는 것(네트워크 장애나 트랜잭션 롤백 시 DB와 캐시가 찢어지는 예외 상황 처리를 고려하지 못함).
    • 예상 꼬리질문: • DB 트랜잭션은 성공했는데 캐시 삭제 명령을 날리는 순간 Redis 네트워크가 일시 단절되어 실패했다면, 두 데이터 간 불일치를 어떤 백업 프로세스로 보완할 수 있을까요? • 캐시의 TTL(만료 시간)을 무조건 길게 잡거나 너무 짧게 잡았을 때 각각 아키텍처적으로 어떤 역효과가 발생하나요?
    • 관련해서 같이 공부할 주제: 트랜잭셔널 아웃박스 패턴, 2차 캐시 전략, 지연 삭제(Delayed Delete) 기법.
    • 중요도: ★★★★★ (고급)
